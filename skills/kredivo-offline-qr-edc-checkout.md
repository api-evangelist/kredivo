# Kredivo offline checkout (QR and EDC)

Accepts Kredivo installment payment at a physical point of sale.

## Choosing a mode

- **Dynamic QR** — a new QR per transaction, generated by your POS through the API. The amount is
  encoded, so the shopper just scans.
- **Static QR** — one fixed QR per store, printed. Requires no development at all, but the shopper
  must key the amount into the Kredivo app manually. If you are not integrating a POS, use this and
  stop here.
- **EDC** — checkout initiated from an EDC terminal against the shopper's mobile number.

Both dynamic QR and EDC use the same operation: `initOfflineCheckout`
(`POST /offline/v1/init_checkout`). Note the offline surface is `/offline/v1/`, versioned separately
from the `/kredivo/v2/` online surface.

## Dynamic QR

Call `initOfflineCheckout` with:

- `server_key`, `amount`, `order_id`, `push_uri`
- `source: "QR"`
- `qr_type` — `IMAGE` returns a QR image URL, `STRING` returns the raw QR string for rendering on
  your own display
- `sub_merchant_id` — the outlet identifier (e.g. `KFCSenayanCity`). Send it; it is how transactions
  attribute to a store in reporting.
- `items[]` and, for marketplaces, `sellers`

Display the returned QR and wait.

## EDC

Call `initOfflineCheckout` with:

- `server_key`, `amount`, `order_id`, `push_uri`
- `source: "EDC Mobile"`
- `sub_merchant_id`
- `mobile_number` — the shopper's phone number, e.g. `+62-85210549044`
- `terminal_id` — optional, the EDC device identifier. Send it; without it you cannot attribute a
  transaction to a specific terminal when reconciling.

The response carries `transaction_id` and `order_id`.

## Resolving the transaction

Identical to the online flow, and just as mandatory:

1. Kredivo POSTs the outcome to `push_uri`.
2. Call `confirmTransaction` with the `transaction_id` and `signature_key` from that notification.
3. **Release goods only when `transaction_status` is `settlement`.**

The offline callback payload additionally echoes `sub_merchant_id`.

This matters more in-store than online: a cashier watching a shopper's phone show a success screen is
not confirmation. Only the `confirmTransaction` response is. Build the POS flow so goods cannot be
released until it returns `settlement`.

If the notification does not arrive, poll `checkTransactionStatus` by `order_id`.

## Reversing an incomplete transaction

If the transaction stalls or the shopper abandons at the counter, call
`reverseOfflineTransaction` with `server_key` and `order_id`.

There is no idempotency key on this operation and no documented replay behaviour — guard against
double submission on your side. Reverse before starting a fresh attempt, and use a new `order_id`
for the retry.

## Testing

Sandbox is `https://sandbox.kredivo.com/`. Be aware that Kredivo's docs show a different sandbox
server key in the QR example (`8tLHIx8V0N6KtnSpS9Nbd6zROFFJH7x`, trailing `x`) than in the
Environment Setup section (`8tLHIx8V0N6KtnSpS9Nbd6zROFFJH7`). Confirm which applies to the offline
surface with `merchops@finaccel.co` before assuming either.
